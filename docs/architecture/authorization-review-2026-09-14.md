# 平台权限现状与建设方案

状态：代码梳理与设计建议，尚未实现。日期：2026-09-14。

更新：用户允许在开发阶段重塑现有体系；实施建议以 [平台权限重塑方案](./authorization-redesign.md) 为准。本文保留现状核查证据。

审查基线：main `f9ac56f`；私有分支 `enterprise/private-hr-integration` `810a14d`。私有工作区另有 SSO 诊断相关未提交修改，本次未改动。以下路径相对仓库根目录。未查询用户业务数据、修改实际授权或运行权限迁移。

## 1. 结论

已有动作码、资源范围、租户隔离、会话归属和审计基础，应在其上补齐平台默认权限与管理语义，不另造一套鉴权系统。

目前“有效员工身份”与“拥有 Agent 使用授权”是两件事：新员工能够进入自己的聊天，但没有直接授权时，Agent 列表会被过滤为空。现有 Member 模板包含 Studio 访问能力，不能直接作为所有员工的默认角色。

建设顺序：先统一员工默认能力、后台角色管理和企业授权扩展，再在智能体管理中加入使用范围。后者的数据语义需在第一阶段确定，以免未来再次修改授权算法；其配置界面可以后做。

## 2. 当前链路与代码证据

| 环节 | 当前行为 | 代码入口 |
|---|---|---|
| 登录与员工身份 | 同步 UserIdentity，建立 PrincipalBinding；此路径没有赋予 Member 或 Agent grants；停用员工拒绝继续业务请求 | `lib/identity/resolver.ts`，`principal-binding-queries.ts` |
| 员工会话 | 列表按租户和当前用户查询，发送前校验会话 owner；无 Agent 时不要求 agent.invoke | `app/api/v1/threads/route.ts`，`threads/[thread_id]/turns/route.ts` |
| Agent 列表 | 从直接 grants 计算 agent.invoke 覆盖，再过滤目录；缺覆盖时不返回 Agent | `app/api/v1/catalog/options/route.ts`，`lib/catalog/catalog-queries.ts` |
| Agent 可执行性 | 员工目录还要求 Agent 启用、未删除、有当前版本，以及相应路由 eligible | `lib/catalog/catalog-queries.ts` 的 employee Agent 门禁 |
| 指定 Agent 调用 | 创建 Turn、写入幂等记录之前重新校验具体 Agent 的 agent.invoke | `app/api/v1/threads/[thread_id]/turns/route.ts` |
| 授权判断 | RoleActionBinding 是当前 action/scope 权威来源，未知动作、缺 grants、非法范围拒绝 | `lib/identity/authorization.ts` |
| 后台权限 | 页面/导航按动作控制展示，API 仍独立校验动作；菜单不是安全边界 | `lib/identity/studio-access.ts`，`lib/studio/nav-visibility.ts` |
| 角色管理 | 平台设置已有成员与角色，选择 Admin/Member；保存需要 user.manage | `components/studio/settings-user-role-manager.tsx`，`app/studio/api/settings/users/[id]/roles/route.ts` |
| 角色持久化 | 模板展开为直接 grants；反向通过 grants 全集推导模板，没有独立的角色成员关系 | `lib/identity/role-templates.ts`，`settings-queries.ts` |
| 企业身份扩展 | 提供 authenticationProvider、可选 profileSource，尚无业务授权决策接口 | `lib/identity/identity-extension.ts`；私有 `lib/deployment/enterprise-sso-provider.ts` |
| 企业资料要求 | 控制资料新鲜度和允许传入 Agent 的字段，不负责判断部门是否能使用 Agent | `lib/identity/enterprise-user-access-policy.ts` |
| 工具执行权限 | 工具的 allow/pause/block、运行环境和执行绑定属于另一层边界，不能用员工角色取代 | `app/studio/permission-rules/page.tsx`，`docs/architecture/execution-binding.md` |

列表与调用已经复用相同的 grants 来源，但分别实现集合计算和单资源判断。新增默认策略及企业规则时，两者必须同步调整，不能只修列表。当前目录 ETag 包含授权摘要，未来还必须纳入策略与身份事实版本。

## 3. 已确认的缺口

### 默认员工与后台成员混在一起

Member 包含 studio.access、policy.read、analytics.read、workspace.read，以及租户级 agent.invoke。它是现有后台模板，不是纯员工身份。

当前 agent.invoke 有特例：租户级授权可覆盖该租户的具体 Agent。未来加入受限使用范围时，必须明确该范围是调用前置约束，否则旧 wildcard grants 会绕过限制。

### 修改角色会覆盖独立授权

`replaceUserGrantsWithAudit` 撤销目标用户各 user 绑定上的全部有效 grants，再写入所选模板并集。事务和审计是已有优点，但操作对象过宽：未来 Agent 专项授权也会被覆盖。

`RoleActionBinding` 目前没有角色模板、资源分享、人工专项授权等来源字段。不能仅靠当前 grants 集合可靠还原历史来源，也不能把所有旧记录自动猜成某个角色。

### Admin 名称与实际覆盖不一致

`role-templates.ts` 的 Admin 未包含 agent.publish、policy.publish 等动作；初始化管理员则由 `lib/db/seed.ts` 的多组动作及导航映射产生更大覆盖。因此“初始化管理员”和后台选择“Admin”不等价，保存后可能丢失已有权限。应建立统一的后台角色定义，导航只消费权限，不能成为角色权限的权威目录。

### 企业部门、岗位授权尚未接通

PrincipalBinding 已有组织主体的建模意图，但 `expandPrincipalBindingIdsForUser` 实际只按 tenantId、userIdentityId 查询绑定，没有部门或岗位成员解析。不能因为表里能写 department，就声称支持按部门授权。

现有 IdentityExtension 也未提供授权接口。企业资料同步、资料字段投影、业务使用授权需要分别命名与执行，避免误用 EnterpriseUserAccessPolicy。

### 不同资产不能一律默认公开

当前目录的 agent.invoke 过滤只针对 Agent，非 Agent 条目不经过这个门禁。不能把“Agent 默认员工可用”机械扩展为所有技能、工具、知识、凭证都可访问。后续应按员工入口逐项核对读、用、改和底层数据权限。

## 4. 建议的平台默认规则

这里的员工指经过受信认证、属于当前租户且未停用的成员，不包含匿名访问者或任意外部注册者。

| 能力 | 普通员工默认 | 附加条件 |
|---|---|---|
| 进入员工 Web/Desktop、管理自己的会话 | 允许 | 租户有效、身份有效、owner 校验 |
| 不选择智能体的基础聊天 | 允许 | 模型、配额、执行策略仍生效 |
| 发现并调用面向员工发布的 Agent | 允许 | 已启用、版本及路由可用、满足使用范围及企业规则 |
| 草稿、停用、内部调试 Agent | 不通过员工入口开放 | 发布状态与使用权限分开判断 |
| 他人的会话与附件 | 不因默认员工身份开放 | 仅已有明确分享或其他正式授权路径可用 |
| Studio 管理页面与修改操作 | 默认不开放 | 单独授予后台角色 |
| 工具执行与知识/业务数据访问 | 不由员工身份直接放开 | 工具策略、执行绑定、数据系统授权继续生效 |

员工默认规则应作为明确、版本化的平台策略参与求值，不在每次 SSO 登录时批量插入 wildcard grants，也不将“空 allowlist”重新解释为允许全部。

“已发布”必须区分可执行版本发布与面向员工的使用发布。最终使用范围建议为“继承平台默认 / 指定范围”；指定范围为空时拒绝，不回退为全员。

## 5. 统一决策顺序与企业扩展边界

建议同一个服务端授权模块同时提供单资源检查、列表过滤依据和管理员可读的决策原因：

1. 平台硬边界：租户、身份状态、资源归属、会话 owner 等校验不允许企业覆盖。
2. 功能权限：员工默认能力或正式后台角色决定可以发起哪些动作。后台管理动作不因员工业务授权扩展而获得。
3. 资产使用范围：受限资产必须命中其指定范围；通用调用 grants 不绕过这个约束。管理员维护资产也不天然意味着可以代替员工读取其业务数据。
4. 企业业务规则：未配置时使用平台策略；已配置时在声明的业务范围内由企业规则作出决策。明确拒绝、所需事实缺失、超时或错误均不能回退为默认允许。
5. 运行与数据边界：版本、路由、工具权限和下游数据权限继续独立生效。

企业可以替换“哪些员工属于业务使用人群”的判断，不能把任意 allow 当作跳过上述所有步骤。扩展应明确覆盖的动作/资源域；域外沿用平台策略，域内返回 allow/deny，不能把运行失败伪装成“未实现”。

实现复用已有服务端组合根、动作码及资源范围，不建设独立权限服务。企业实现留在私有分支，部门、岗位等稳定标识与资料来源也由企业提供。列表查询需要批量决策或可下推的范围，不能逐条远程请求后随意过滤分页。

缓存必须绑定租户、主体、平台策略版本、资源范围版本以及企业事实/决策版本。撤权后的新调用重新检查；已运行任务如何处理沿用执行治理机制，不能宣称清理页面缓存就实现实时撤权。

## 6. 管理交互安排

沿用当前满意的页面样式，不新增独立的“给某人授权某 Agent”页面。

- **平台设置 → 成员与角色**：区分默认员工身份与额外后台角色；保存角色只变更该来源的授权。角色名称、说明、实际动作覆盖必须一致。
- **平台设置的现有权限相关区域**：展示普通员工默认能力和企业接管状态。第一阶段固定一套清晰的默认规则即可，不先做任意规则编辑器。
- **智能体管理 → 智能体详情**：后续加入“使用范围”，默认继承平台；受限范围在这里维护。企业组织选择复用统一主体选择能力。
- **成员详情或已有成员操作区**：提供针对具体动作/资产的权限说明，例如“员工默认允许”“范围不匹配”“企业策略拒绝”，复用同一决策结果，不另算前端权限。

员工侧不泄露不可访问的资产详情；后台有权限的管理员才查看完整原因。目录为空还可能是未发布或路由不可用，不能统一提示“请联系管理员授权”。

## 7. 实施顺序与迁移

| 阶段 | main 通用工作 | 私有分支工作 | 完成标准 |
|---|---|---|---|
| 一：平台权限基础 | 统一角色定义，增加员工默认规则、授权来源及统一决策；修复角色全量覆盖；补齐列表/调用/缓存一致性 | 合并并验证 SSO 新员工，不写企业部门特例到 main | 新员工可基础聊天并使用明确面向员工的 Agent，无需 SQL，默认无 Studio 权限 |
| 二：企业业务规则接入 | 可选授权扩展合同、批量求值、失败原因与缓存约束 | 对接真实部门/岗位事实与业务规则 | 未配置用默认；已配置失败拒绝对应能力；跨租户始终拒绝 |
| 三：资产使用范围 | 在 Agent 详情实现使用范围，复用统一授权与主体模型 | 接通企业组织选择/解析 | 设置后列表与调用同时生效，改角色不误删资产授权 |

阶段一需先通过隔离 MySQL 回归建立失败证据，再修改鉴权逻辑与迁移。旧 grants 保留为可追溯的历史直接授权；能够确定来源的记录才迁移归类，不能按包含某模板的集合就批量撤销。

现有存量 Agent 不在迁移时自动全部公开。新默认规则与旧资产开放是两项不同变更：需要先列出待面向员工发布的资产及敏感性，再按明确范围迁移。这样既补齐平台能力，也不意外扩大已有 HR 资产权限。

角色治理需同时保留已有防自锁/最后管理员保护及审计事务，并覆盖并发修改冲突。身份停用、部门变化、角色撤销应触发相关授权缓存失效。

## 8. 验收清单

- 新本地/SSO 员工无人工 grants：可进入自己的聊天，未选择 Agent 也可正常完成任务；默认不能进入 Studio。
- 面向员工且可执行的 Agent：列表可见、直接调用可用；草稿、停用、非员工发布资产不能因默认规则露出。
- 指定范围命中/不命中/空范围：列表和直接 API 调用一致；旧 tenant wildcard 不绕过限制。
- 修改后台角色：保留资源专项授权和其他来源授权；初始化管理员与同名后台角色能力一致。
- 停用用户、跨租户资源、他人会话：拒绝，且不产生新的 Turn 或副作用。
- 企业扩展未配置、明确拒绝、事实缺失、超时、异常：分别验证，不把异常降级为开放。
- 部门/岗位变化与撤权：旧 ETag、缓存及旧页面不能继续发起未授权调用；列表分页不会漏页或泄露资产数量。
- 员工角色不绕过工具审批、执行隔离、凭证限制和下游 HR 数据权限。
- 从真实管理入口调整权限，再用另一个真实测试员工会话检查前后状态；沿用当前界面风格。
