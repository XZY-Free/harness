# 平台权限重塑方案

状态：2026-09-14 实施中。下文保留设计目标；已落地边界与验收见文末，不能把目标描述当作运行证据。

本方案基于用户允许在开发阶段重塑权限体系的决定，替代 [权限梳理](./authorization-review-2026-09-14.md) 中以保留旧 grants 为前提的实施建议；原文的现状证据仍有效。补充核查 main `827312f`：相对原基线仅新增身份上下文错误提示改动。现有页面视觉保持不变。

## 1. 产品目标与取舍

新员工经受信登录后即可聊天、使用面向全员发布的资产，不需要管理员逐人授权。需要限制时，在资产自己的管理界面选择人员或用户组；需要管理平台时，给成员或用户组分配清晰的后台角色。

重塑的重点是明确、可解释且一致的权限语义。允许调整 schema、角色模型、接口和相关组件，不保留新旧两套授权长期并行。不为追求通用性引入独立权限服务器、图数据库或任意策略脚本编辑器。

“一次做好”意味着把模型、交互、企业边界、迁移和验证作为一个完整交付目标，而不是一次提交完成所有改动。分批验证和提交不改变最终统一切换的目标。

## 2. 官方资料调研

以下是官方文档描述，不代表本次已实测各产品，也不保证各版本/套餐均提供这些功能。链接核查于 2026-09-14。

| 对象 | 官方做法 | SnowHarness 的采用方式 |
|---|---|---|
| [Open WebUI RBAC](https://docs.openwebui.com/features/authentication-access/rbac/) | 区分角色、能力权限和群组；群组参与资源分享；默认与群组授权叠加 | 采用默认员工能力、用户组和资产访问关系的分离，不把业务数据权限交给聊天角色 |
| [Langfuse RBAC](https://langfuse.com/docs/administration/rbac) | 组织与项目分层角色；项目角色可以覆盖组织继承；分配角色受操作者权限约束 | 采用全局管理与资源职责分离、限制转授权；不照搬其项目覆盖规则，以免与资产范围冲突 |
| [n8n 角色](https://docs.n8n.io/administer/manage-users-and-access/set-permissions-and-roles-rbac/see-available-roles.md) | 区分实例角色与项目角色；项目 Admin、Editor、Viewer 职责不同，Viewer 不能手动执行工作流 | 采用“管理、编辑、使用不是同一种权限”的语义；不为权限额外引入新的项目层级 |
| [OpenFGA 角色与权限建模](https://openfga.dev/docs/modeling/roles-and-permissions) | 通过角色和资源关系推导权限，业务查询权限而非硬编码角色名 | 借鉴关系模型；用当前 MySQL 和服务端授权模块实现，不直接增加 OpenFGA 运行依赖 |

我的判断：适合本项目的是“少量内置角色＋可配置角色＋资源访问关系＋可选企业约束”。只做角色会导致大量部门专用角色；只做逐人资源授权会让管理员重复劳动；全盘属性策略化又会让普通管理员无法理解。

## 3. 用户看到的权限管理

### 3.1 平台设置中的成员、用户组、角色

保留平台设置入口及现有组件风格，在“成员与权限”区域组织三个视图，不增加顶层权限中心。

| 视图 | 常用操作 | 展示重点 |
|---|---|---|
| 成员 | 搜索、查看状态、调整本地后台角色、查看所属组和有效权限 | 普通员工身份、直接角色、组继承角色、企业托管来源分开展示 |
| 用户组 | 创建本地组、维护成员、给组分配角色 | 一个 HR 组可供多个资产复用；企业同步组只读，不复制一棵企业组织树 |
| 角色 | 查看内置角色、复制创建自定义角色、编辑权限、查看使用成员/组 | 按业务领域呈现“查看、编辑、发布、管理”，动作码仅放详情 |

普通员工是所有有效租户成员的默认基线，界面显示“默认”，不要求逐人打勾。停用账号用身份状态管理，不伪装成没有角色。新登录不自动获得后台管理角色。

权限页面提供“检查权限”：选择成员、动作和资产，展示允许/拒绝及来源。入口放成员详情；资产详情也可复用同一个检查组件。权限预览和实际保存使用同一服务端求值器。

### 3.2 内置角色

| 名称 | 定位 | 边界 |
|---|---|---|
| 普通员工（默认） | 基础聊天、自有会话、使用发布给自己或全员的资产 | 无后台管理能力 |
| 平台管理员 | 成员、角色、系统配置及平台资产治理 | 不读取凭证原值；他人聊天正文、敏感业务数据不因角色自动开放 |
| 资产维护者 | 创建资产、维护自己拥有或被授予协作权限的资产 | 不改平台权限；编辑、发布与管理使用范围按不同动作控制 |
| 审计查看者 | 查看授权变更和运行审计元数据 | 默认无编辑、无敏感正文、无批量导出权限 |

内置角色不能直接改坏，管理员可以复制为自定义角色，例如“HR 发布负责人”。平台管理员的动作集合显式定义并测试，新增动作需要明确归属，不用 `*` 自动继承未来所有能力。初始化管理员与后台赋予同名角色必须一致。

自定义角色是平台职责包，不包含每一个资产 ID。具体资产协作范围单独配置，避免每增加一个 Agent 就新建一个角色。普通管理员不能通过创建角色、修改角色或分配已有角色授出超越自身可转授范围的权力；平台级授权管理能力单独受保护。

### 3.3 资产自己的访问管理

在智能体详情内提供“访问管理”，并分成两个明确区域：

- **使用范围**：继承平台默认（默认全体成员）/指定成员和用户组。新资产发布时在摘要中明确显示范围；草稿无论范围怎么设置都不进入员工目录。
- **协作管理**：维护者、发布负责人等资源职责。能编辑不等于能发布，能管理不等于可以代表任何员工查询数据。

“继承平台默认”实时继承平台设置，管理员修改默认范围前展示受影响的继承资产数量。指定范围为空时不可发布供员工使用，且不会解释成全员。已有发布资产被清空范围后停止接受新的员工调用，不偷偷回退默认。

人员与用户组共用一个搜索选择器。企业已对接部门、岗位时，同一选择器增加对应来源标签，不把企业名称或组织规则写进通用组件。

访问摘要使用自然语言，例如“全体成员可使用”“人力资源部和 2 位成员可使用”“由企业策略管理”。企业规则完全接管的部分只读，明确显示在哪里维护，不给用户一个保存后实际无效的表单。

### 3.4 三条主要使用流程

1. **雷佳首次登录**：成为有效员工 → 直接使用基础聊天 → 可看到面向全员且可执行的智能体。无需先由管理员配置 Member。
2. **HR 限定使用**：管理员建立/选用 HR 组 → 在人力智能体“使用范围”选择 HR 组 → 新成员加入该组后自然获得使用权限。组成员关系可以来自企业同步。
3. **排查无权访问**：在成员详情检查“使用人力智能体” → 显示“未命中 HR 组”或“企业规则拒绝”等原因。员工侧不暴露未授权资产或部门明细。

## 4. 统一的数据和授权模型

### 4.1 模型职责

保留 Tenant、UserIdentity、PrincipalBinding、资产实体、owner 字段与审计基础。增加或重塑以下职责；表名是目标概念，实施时按现有 schema 命名约定落地：

| 对象 | 保存内容 | 关键约束 |
|---|---|---|
| Role | 内置/自定义角色、动作集合、版本 | 租户隔离；角色删除先处理引用；内置定义受保护 |
| RoleAssignment | 主体到角色的正式分配 | 主体可以是人或组；记录来源和有效期，不再从 grants 集合反推角色 |
| 用户组及成员关系 | 本地组成员、企业主体映射 | 复用 PrincipalBinding 作为主体；本地与企业来源隔离；初版不开放任意嵌套组 |
| ResourceAccessPolicy | 资产继承/指定范围及版本 | 绑定稳定资产 ID；版本发布不悄悄重置使用范围 |
| ResourceRelation | 成员/组与资产的使用、维护、发布等关系 | 同租户；区分角色职责与具体资源范围；操作审计 |
| 平台默认策略 | 默认员工能力、面向员工资产的默认范围 | 有版本，变更影响可预览；不是“缺策略则全放开” |

已有 RoleActionBinding 不继续担当“角色成员事实源”。旧直接授权要么一次转换为正式角色分配/资源关系，要么作为待处理迁移项；完成切换后移除旧 grants 写入与推导路径。企业实时资料不是另一份可被本地编辑的用户档案。

### 4.2 授权组合

同一层的多个正向来源取并集，不引入四处可配置的 allow/deny 优先级。层与层之间取交集：

```text
最终允许
  = 身份、租户与资源硬边界通过
  ∩ 具备发起该动作的功能权限
  ∩ 满足该资源的访问或协作关系
  ∩ 企业接管域的决策通过（若已接管）
  ∩ 发布、执行及下游数据要求通过
```

拥有资源的 owner 是协作关系来源，不代表有权改变平台角色或绕过企业业务拒绝。具备租户级“管理 Agent”职责也不等于员工侧使用所有受限 Agent。

有效员工默认有基础聊天能力；没有选 Agent 时不经过 Agent 使用校验。有指定 Agent、自动选择、委派、恢复或重试时，只要发生新的受保护调用，就必须在可信的调用边界检查当前用户的有效权限。不能只覆盖目录和手动选择入口。

Workload/Service 身份继续独立验证；Agent 不通过携带用户声称的角色来提权。每次受保护调用需要明确是代表哪个用户，或使用哪一个受约束的服务身份。用户授权与执行绑定取交集，不能用一张全能服务凭证代替用户权限。

### 4.3 统一的服务端能力

扩展已有 `lib/identity/authorization.ts` 为唯一权限求值入口，提供：单对象授权、列表可见范围、决策解释。不是三个独立算法。

- 所有数据查询先限定租户。列表在数据库分页前施加本地范围，企业批量过滤需要能继续扫描到合法页或明确返回游标，不能固定抓一页再过滤。
- 角色/分组/资源策略/企业事实版本进入缓存键和目录 ETag。授权撤销后，旧 UI 不能继续成功提交受限请求。
- 未配置扩展、明确拒绝、依赖不可用分别记录；故障不缓存成永久业务拒绝，也不返回允许。
- 授权拒绝在创建 Turn、幂等结果及副作用之前完成；长任务在下一次受保护操作边界重新检查。已经完成的操作不宣称可逆。
- 管理写入在同一事务内校验权限与版本、修改关系、写审计；最后管理员保护要在锁或等效并发控制下保证，不能事务外先数人数再写。

权限目录统一动作标签、领域、资源类型、可转授属性和审计要求。导航、角色编辑器、初始化脚本都读取该目录，不再各自维护不一致的动作列表。清查当前看起来类似事件名的 `admin.export.requested/completed/failed` 等条目，确认调用方后再决定是否应属于可分配权限，不凭名称直接删除。

## 5. 企业接管方式

推荐默认接入方式是：企业提供可信主体、部门/岗位/组成员关系，平台仍负责统一角色和资源授权。这能保留同一套管理和诊断体验。

企业已有独立权限系统时，允许通过现有服务端组合根接入授权提供器，并声明接管哪些业务动作/资源。接管域内的决策权交给企业；域外仍由平台负责。这个扩展不能覆盖租户隔离、身份停用、凭证边界等约束，也不能根据企业返回的任意角色名直接授予平台管理员。

默认策略如下：

| 状态 | 行为 |
|---|---|
| 未配置企业授权 | 完整使用平台权限功能 |
| 仅提供组织资料 | 用可信组关系参与平台求值 |
| 明确接管业务域 | 平台与资源硬约束通过后，要求企业允许 |
| 已接管但异常、超时、必需事实缺失 | 拒绝该业务能力并解释依赖问题；基础聊天不因一个 Agent 域故障全部瘫痪 |

企业托管角色或组成员在本地显示来源和更新时间，不能通过本地保存覆盖掉。组织撤员或调岗要同步撤销旧关系，不能只增不减。部门选择中的“包含下级部门”必须明确表达，并由企业资料提供方解析；不能靠名称前缀猜组织层级。

main 只实现合同、平台默认实现和真实可测的管理能力。私有分支接入实际企业资料与规则。尚无可调用企业权限接口时，不编造一个成功返回的适配器；先使用平台权限与已验证的企业组事实。

## 6. 开发阶段的替换与交付安排

允许一次重塑，不表示可以删除用户正在测试的数据。优先在隔离 MySQL 中验证全新 schema 与旧数据转换，正常开发库保留现有用户、会话和资产。

1. **确定权限目录与数据模型**：按现有路由和调用边界完成动作清单；写决策表回归，替换反推角色和无来源 grants 模型。
2. **贯通全部服务端入口**：默认员工、后台、目录、手动/自动 Agent 调用、工具和知识引用；清理旧绕行路径。
3. **完成平台设置管理体验**：成员、组、内置/自定义角色、权限解释；复用现有组件，保存前显示权限变更摘要。
4. **完成 Agent 访问管理**：使用范围、协作关系、发布摘要；首个资产端到端落地，同时为其他受保护资产复用相同模型。每个资产类型只暴露其真实支持的动作，不复制 Agent 页面。
5. **接通企业扩展与迁移切换**：main 通用能力验证后合并私有分支，接入真实企业事实，确认旧角色/授权全部转换后移除旧实现。

这五项属于同一完整目标。实施时分成可回归的提交，不能用“平台基础完成”代替管理员真正能用的页面，也不能用空扩展接口宣称企业接入完成。

新资产草稿默认不面向员工；首次员工发布默认全员并明确显示。存量资产按显式迁移清单确定范围，不将旧“有 published revision”等同于“已同意全员使用”。无法推断来源的旧 grants 形成脱敏迁移报告，由开发阶段的明确映射处理，不把它们永久保留成第二套权限系统。

旧 Member 不直接升级为资产维护者或管理员；有明确后台管理事实的账号保留对应权限。操作前比较迁移前后授权差异，意外新增权限必须为零。若需要清空测试库重新初始化，应单独明确目标测试库，不影响现有联调数据。

## 7. 实施入口与验证

核心路径：`lib/identity/{authorization,role-templates,role-action-queries,settings-queries,studio-access}.ts`、`lib/persistence/schema/{identity,authorization}.ts`、`lib/studio/{role-safety,nav-visibility}.ts`、`lib/db/seed.ts`、员工 Catalog/Turn API、`lib/agents/calls/application/`、Studio 设置与 Agent 详情。

组件复用：`StudioSettingsSection`、`StudioSettingsRow`、`SettingsUserRoleManager` 的布局能力，以及现有 `Button`、`Checkbox`、`Tabs`、`Dialog`、`Command`、`Popover`。新增共享角色编辑和主体选择能力，不手写第二套弹窗或重复 API 客户端。Next.js 改动前读取安装版本的相关指南。

验收必须覆盖：

- 新账号无直接 grants 完成基础聊天；全员发布 Agent 可发现可调用，后台默认不可进入。
- 加入/移出组、分配/撤销角色、修改范围、停用身份后，列表与调用同步生效。
- 多来源授权只撤销自己的来源；同一个人被另一个有效组授予权限时，界面解释其剩余来源。
- 自定义角色不能提权；修改自身或并发修改两个管理员不造成平台无人可管。
- 全员范围、指定范围、空范围、草稿、停用、跨租户、他人会话与附件分别验证。
- 自动调用与手动调用具有同样边界；恢复/重试不复活已撤销权限。
- 企业托管字段不可本地覆盖；超时、异常、陈旧事实和明确拒绝分开验证。
- 角色修改与审计失败均事务回滚；分页、授权缓存和版本冲突有回归。
- 不登录数据库改权限：在真实管理页面操作，再用真实测试员工验证；保持现有视觉与窄屏布局。

仓库现有命令：`pnpm exec vitest run <相关测试路径>`、`pnpm typecheck`、`pnpm architecture:check`、`pnpm build:test`、`pnpm test:e2e`。数据库回归按项目要求使用隔离 MySQL；实施时核实测试配置后执行，不将 mock 通过当成真实授权链路通过。

本次交付为有来源的目标方案及实施边界。未执行 schema 迁移、权限赋予、页面改动或行为测试。


## 9. 当前实现与运行边界（2026-09-14）

主分支已实现正式角色分配、本地/企业用户组、平台默认范围、智能体使用及协作范围，以及统一服务端求值。管理入口为「平台设置 → 成员与权限」和「智能体详情 → 访问管理」，沿用现有页面组件。

数据模型采用 `PermissionRole`、`PermissionRoleAssignment`、`PermissionGroup`、`PermissionGroupMember`、`ResourceAccessPolicy` 五张表；资源协作关系保存在策略的 collaborators 中，不再另建关系表。默认员工只提供自有会话能力；后台管理角色不自动授予他人会话或敏感导出权限。当前资产访问编辑器仅接入智能体，不能据此宣称其他资产已有同样的使用范围界面。

`0001_permissions.sql` 增量建表；应用启动的 `runMigrations()` 随后事务转换 `RoleActionBinding` 为正式自定义角色及分配，保留每条动作、资源范围、生效/到期时间。转换失败全部回滚。存量智能体使用 `roles` 模式保留原授权，新建智能体显式写入 `inherit`。不会把存量 HR 智能体自动开放给全员。旧表仅供迁移读取，运行时不再读写；不要仅运行 drizzle CLI 后省略应用数据迁移。

角色变更、组成员调整和策略保存使用租户事务锁、版本检查、转授权范围检查及同事务审计。目录、实际调用、等待用户补填后的恢复均重新读取当前权限；权限撤销后不会继续向外部智能体发送恢复请求。

企业资料继续存入 `UserExtensionAttribute` 和现有同步状态表。可信 `authorizationGroups` 是经过字段目录校验的派生输入；与资料写入同一事务更新企业成员关系。企业组成员只读，资料过期或来源/归属变化移除旧关系。本地成员关系不受此同步覆盖。部门/业务单元名称、岗位及来源集合标识都有明确字段；不存原始认证响应、token 或密码。

可选 `IdentityExtension.authorizationProvider` 接受声明范围内的智能体批量决策，与平台授权取交集；缺少决策、过期资料、异常和超时默认拒绝。这是可用扩展合同，当前没有企业在线权限接口，不能声称已接通企业 PDP。部门与业务单元通过可信资料同步成组，不借组织字段自动分配管理员。

管理接口复用 Studio 身份与权限门禁：`GET/POST /studio/api/settings/permissions`（列表、角色/组/默认策略变更及解释），`GET/PUT /studio/api/agents/{id}/access`（资产负责人或权限管理员）。所有主体必须属于当前租户。

验证包含隔离 MySQL 迁移幂等/回滚、默认员工、跨租户、组继承、并发撤权防自锁、审计失败原子性、企业资料与关系同步、调用与恢复撤权，以及实际应用的用户组创建保存。完整页面连续操作和私有 SSO 落库验收仍在执行；目标章节中的发布摘要、全部资产类型覆盖不属于已验证事实。
