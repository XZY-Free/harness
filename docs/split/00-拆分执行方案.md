### 1.1 三个项目

| 3 | **auth-center** | `~/IdeaProjects/auth-center` | `XZY-Free/auth-center`（新仓） | **完整身份平台**：统一登录（登录/会话/密码/SSO/设备登录）+ 用户目录 + 角色数据 + 生命周期治理 + 登录门户 + 管理台 + 19 张表（身份域 13 + 生命周期治理 6） |

### 1.2 双形态（三项目通用）

- `main` ↔ **GitHub**（通用版）；私有分支 ↔ **公司 CNB**（企业版，UAT 部署）。
- 企业部署现状（④ 之前不得破坏）：CNB `python-service` 大仓的 `snow_harness` 子目录 = 企业私有版部署载体；`.cnb.yml` 的「SnowHarness 全套」入口构建 **snowharness-web + 4 个 worker** 共 5 个 Deployment 到 UAT K8s；Nacos 配置；企业库 `ctp_rbac`；活跃部署工作区 `~/.config/superpowers/worktrees/cnb-python-service/snowharness-deploy`。

### 1.3 数据边界（同库）

- 135 张表 = **auth-center 19 张**（identity 7 含 tenant + authorization 6 + 合规模块 6）+ **nexharness 116 张**。
- **表归属**：身份域 13 张（含 `tenant` 租户/组织根——属身份域，归 auth-center）+ 合规模块 6 张由 auth-center 管理；其余 116 张归 nexharness。
- **消费方模型（2026-10-14 拍板；替代"只读引用面"方案）**：
  - auth-center = 身份 / 权限 / 治理的唯一权威（19 表 + 全部评测算法 + 企业扩展）。
  - nexharness = **纯消费方**（与未来业务系统同一套接入模式）：经 `identity-client` 消费——会话校验（introspect + 缓存 30~60s）、权限快照（缓存 5~15min + 本地清单匹配）、变更/敏感操作实时 `authorize`、目录读（批量 + 分钟级缓存）。
  - nexharness 保留的唯二身份相关物：① **FK 目标 stub**（`tenant` / `user_identity` / `principal_binding` 的 id 列——104 处外键的数据库完整性需要，非数据非逻辑）；② 协议词表（action codes 常量）。
  - 安全语义：变更类操作 **100% 实时**校验（不降级）；读类窗口 ≤ 快照 TTL；auth-center 不可达 → 实时操作 fail-closed。
  - 开发/测试建库：身份表由 auth-center 迁移产物创建（外键前置）；nexharness 侧 116 表基线不变。
  - 注意：auth-center 成为**运行时依赖**（agent 执行链授权实时调用）——服务化模型的必然；开发/联调双起（既定姿势）。

### 3.0 形态与完整性（不最小化）

- **目标结构**（完整产品，全新仓库）：

```text
auth-center/
  server/                       # Hono API 服务（Node 22+）
    src/auth/                   # 认证 6 操作 + 会话签发/校验
    src/users/  src/roles/      # 用户目录与角色数据
    src/lifecycle/              # 生命周期治理（deletion/retention/legal-hold/incident）
    src/extension/              # 双形态装配口子（启动期 provider 替换）
    drizzle/                    # 身份与治理 19 表迁移（自持）
  web/                          # Vite + React：登录门户（SSO 回调、外部认证区）+ 管理台
  tests/                        # （暂不生成——待用户重新定义项目后建立）
```

- **技术形态（2026-10-14 已拍板：不用 Next.js）**：
  - **已定：Hono（API 服务）+ Vite + React（登录门户 + 管理台）**。同仓 `server/` + `web/`，一个部署单元（Hono 伺服静态产物）。
    - 理由：① 职责匹配——“API 重、页面轻”，不需要 SSR 框架；② **与 nexharness-client 同构**（统一 Vite + React，组件与设计语言一致）；③ **测试友好**——Hono 的 `app.request()` 可直接对 HTTP 断言，利于完整测试基座；④ **双形态更顺**——启动期装配 provider 替换，优于构建期替换；⑤ 依赖轻、构建快、部署简单。
  - 备选（未采用）：Fastify + Vite + React——如以后需要更传统的安全插件生态可再评估。
  - **不采用**：NestJS（过重）；现成身份产品（Keycloak/Zitadel 等——与“完美复刻 + 双形态 + 企业定制”冲突，重构成本最大）；继续 Next.js（90% 能力用不上，且与客户端项目不同构）。
  - **迁移说明**：登录 UI 组件（components/auth）基本直接搬（next/* 引用替换为 react-router 等）；`app/api/auth` 的 6 个认证操作改写成 Hono handler（体量小）；管理台照搬 React 组件；会话/密码/角色/治理逻辑均为框架无关的纯 TS，直接复用。

### 3.2 接口契约 v2（消费方接口集）

| 能力 | 接口 | 消费者侧用法 |
|---|---|---|
| 登录跳转 | `GET {auth-center}/login?returnTo=<url>` → 302 带回一次性 `ticket` | 所有系统统一入口 |
| 票据兑换 | `POST /api/session/resolve { ticket }` → `{ principal, snapshot }` | 登录时换取身份与权限快照 |
| 会话校验 | `POST /api/session/introspect`（cookie/token）→ `{ principal, expiresAt }` | nexharness 每请求校验，**本地缓存 30~60s**；实时操作绕过缓存 |
| 登出 | `POST /api/session/revoke` | 登出 = 撤销 + 清本地缓存 |
| 权限快照 | `GET /api/permissions/snapshot` → 展开后的允许清单（action → 资源 id / wildcard / self） | 懒加载 + 缓存 5~15min；本地清单匹配（无模板/作用域推导） |
| 实时授权 | `POST /api/authorize`（单/批）→ `{ allowed, reason }` | **变更/敏感操作 100% 实时**；agent 执行链授权决策 |
| 目录读 | `GET /api/directory/users/:id`、`POST /api/directory/users:batch` | 显示信息，分钟级缓存 |

- 安全语义：变更类实时 fail-closed；读类窗口 ≤ 快照 TTL；未来增强 = 写时失效推送。
- 会话机制默认 **introspect + 缓存**（服务端保留撤销权威）；备选"签名令牌本地验签"——实现时再评估。

### 4.3 Vite SPA 化（选型理由）

> 为什么推荐 Next.js 页面 → Vite + React：
> 1. **与桌面端同构**：desktop renderer 已是 Vite + React；统一后一套构建、一套组件复用（现状是两套工具链共享组件，有摩擦）。
> 2. **产物匹配独立部署**：Vite 产出纯静态文件——静态托管最轻（nginx/CDN/对象存储），无 Node 运行时需要运维；与"方案 A（前端自己发）"天然匹配。
> 3. **Next.js 的核心价值用不上**：SSR/RSC/SEO/服务端数据直连对本内部平台无价值；而 RSC 直连恰恰是拆分要消除的耦合（页面数据 API 化的成本无论如何都要付）。
> 4. **心智统一**：切到 SPA 后"客户端渲染 + 调 API"一种模式，不再有 server/client component 边界问题；路由量级（chat/studio/admin）react-router 足够。
> 5. **更轻的依赖面**：去掉 Next.js 全家桶在客户端项目中的重量，构建更快。
> 代价：21 个页面壳重写 + 数据获取改客户端 fetch（本来就要做）；CSR 首屏（内部平台可接受）；自建 dev 代理与路由守卫。备选（保留 Next.js 独立服务）成本更低但与桌面不同构、多一个 Node 服务——不推荐。

- 路由映射：`/chat/[threadId]`、`/studio/*`、`/admin/*`、`/preview` 壳。
- 数据层：复用 `lib/api-fetch` + `lib/control-plane-client`；页面数据全部改为对 nexharness API 的 fetch。
- 构建产物为静态文件；dev server 代理 API 到 nexharness。
